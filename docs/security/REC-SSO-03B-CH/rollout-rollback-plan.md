# Activación y reversión propuestas — NO EJECUTADAS

1. Mantener bloqueados despliegue, staging/producción, escrituras compartidas y migraciones. Obtener mandato separado para dichas operaciones; este documento no es aprobación.
2. En laboratorio desechable autorizado, revisar/aplicar `integration.0008_ssoclient` y verificar FK, OneToOne, unicidad de client_id/audience y tabla M2M. El estado de migración se comparó offline con modelos; la persistencia PostgreSQL está NOT_EVIDENCED.
3. Provisionar claves RSA distintas: autoridad central, ISO Smart y MedSupplier. Registrar huellas públicas fuera de logs de credenciales. Consumidores reciben solo claves públicas centrales; jamás privada central. Verificar también distinción entre ambas claves locales durante el provisionamiento.
4. Configurar `SSO_CENTRAL_TRUST` y, en consumidores, `SSO_LOCAL_TRUST`; configurar receiver ADMIN_APPS_SSO y credencial dedicada. No reutilizar SMART3AI_SSO_JWT_SECRET/SECRET_KEY/SIMPLE_JWT. Las claves en pruebas son efímeras sintéticas en memoria.
5. Crear SSOClient inicialmente deshabilitados con principal hashed_v1 exacto, producto activo, audiencia exclusiva, issuer central, kids autorizados y tenants explícitos. Validar el contrato y habilitar únicamente tras validar el conjunto. Una lista de tenants vacía no concede acceso. La rotación de credencial requiere reasignación deliberada de OneToOne; no se hereda por nombre.
6. Reconciliar mappings UUID central/usuario local autorizados. No usar emails o slugs para repuntar identidades. Verificar permisos de tablas/servicios; no se afirma diseño de RLS específico del registro global aplicado.
7. Ejecutar HTTP/E2E: ambos productos, login/challenge/TOTP/backup, HttpOnly/CSRF, bearer MedSupplier, introspección, expiración/refresh/rotación/switch, revocación, caídas, roles y concurrencia. Ejecutar versiones mixtas y ensayo de reversión. Evaluar tamaño real de cookies: la sesión conserva prueba central embebida.
8. Coordinar ventana de corte de las tres aplicaciones y reautenticación obligatoria. CH dura como máximo 300 segundos de prueba central y no ofrece renovación central silenciosa; validar impacto de UX/carga antes del corte. Nunca instalar API keys en frontend.
9. Ante incidente de activación: deshabilitar emisión/acceso de clientes afectados y mantener rechazo cerrado. Volver a una versión CH comprobada o detener el acceso. No aceptar tokens viejos ni reactivar secretos compartidos como fallback. Revertir a Decision A implica renunciar a garantías C/H y exige decisión explícita de autoridad; no se propone como reversión segura automática.
10. Conservar tabla y filas para auditoría: no ejecutar rollback destructivo de esquema ni borrar historia. Revocar credenciales/keys introducidas solo con autorización de su custodio. Validar reautenticación y aislamiento antes de restaurar tráfico.

Pendientes externos: aplicación de esquema, filas reales, provisioning y distribución de claves, configuración de confianza, laboratorio PostgreSQL y HTTP, decisión de corte. Ninguno ejecutado. B (sesiones/revocación durable) y D (scopes) siguen abiertos.
